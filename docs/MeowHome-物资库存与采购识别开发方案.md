# MeowHome 物资库存与采购识别开发方案

编制日期：2026-10-22。本文是基于当前仓库实现提出的开发方案，不代表下述功能已经实现。首期以微信小程序为主入口，H5 后续复用同一后端 API。

## 1. 目标与定位

让家庭成员能够维护“准备买什么”，并通过淘宝、京东等平台的订单截图快速整理已购买商品。系统识别后生成可编辑草稿；用户核对并确认后，才更新库存、记录采购支出和完成对应待购项。

核心数据分为三类，不能混成一个状态：

1. **待购买清单**：用户计划采购的物品，不代表家里已经有货。
2. **当前库存**：家中现有数量、单位、分类、低库存阈值和到期信息。
3. **采购记录**：某次实际订单及其商品明细，是库存入库和支出记账的来源。

首期不接入电商账号、不抓取平台订单、不自动下单。识别截图不直接写入正式库存或支出。

## 2. 当前项目基线

| 区域 | 当前实现 | 本需求的差距 |
|---|---|---|
| 家庭入口 | 家庭页已有“物资库存”卡片 | 卡片目前展示库存数量，没有待购买数量 |
| 小程序库存页 | 展示需关注和全部库存 | 目前以只读列表为主，没有待购清单、添加流程或采购导入 |
| 后端库存 | `inventory_items` 有名称、分类、数量、单位、阈值和到期日；有列表、新增 API | 缺少待购领域和采购导入 API |
| 库存流水 | 数据库已有 `inventory_transactions` 表和仓储接口 | 当前库存新增/调整流程没有通过流水完整维护数量，尚不能依流水重算 |
| 支出 | 有家庭支出列表和新增能力 | 采购订单与支出没有关联，缺少重复导入防重 |
| 图片与 OCR | 有 OCR 配置结构；头像上传会写本地存储 | 没有通用私有媒体上传、订单截图 OCR Provider 或采购识别流程 |

## 3. 用户与场景

- 家庭成员发现猫粮、猫砂或清洁用品快用完，快速加入待购买清单。
- 家庭成员在淘宝、京东等平台完成采购后，上传订单详情截图，不再逐项手工录入。
- 家庭成员检查识别出的商品、规格、数量和实付金额，决定哪些商品计入库存，并确认记账。
- 家庭成员在库存页查看当前数量和需补充项目；采购确认后，待购状态和库存可以对应更新。

## 4. 首期范围

| 纳入首期 | 暂不纳入首期 |
|---|---|
| 家庭级待购买清单，支持手动增删改和完成状态 | 绑定淘宝/京东账号或读取平台订单 API |
| 手动创建和调整库存，并记录库存增减流水 | 自动下单、比价、商品推荐或自动补货 |
| 上传订单截图，识别平台、订单日期、实付金额和商品行 | 取消订单、部分退款、复杂满减分摊的自动处理 |
| 识别结果可修改、可选择入库和待购匹配 | 识别后不经确认直接更新正式业务数据 |
| 确认后写库存流水和可选的订单支出，保证幂等 | 根据库存推算消耗速度或生成医疗/喂养建议 |

首期优先支持清晰的淘宝、京东已支付订单详情截图。不同版本的页面布局会变化，平台识别只作为辅助信息；低置信结果允许用户手工修正或直接手动记录。

## 5. 页面与交互

### 5.1 家庭页入口

保留截图中的“物资库存”卡片作为主入口。卡片数值建议展示待购数量，副文案展示低库存数量，例如“待买 3 项 / 2 项库存不足”。若待购为空，则继续展示当前库存总数，避免让空清单看起来像异常。

### 5.2 库存管理页

页面顶部使用分段页签“库存 / 待购买”。库存页继续展示当前的需关注分组和全部库存；待购买页显示待购项、数量和单位、添加人、备注及状态。页面主要操作为“添加物资”和“识别订单截图”。库存条目提供“调整数量”入口，所有变化都留下流水。

手动添加表单首期字段：物品名称、数量、单位、分类、备注。可选关联已有库存项。加入待购项不改变库存数量；标记为已购买时，可选择只完成待购、更新库存，或同时录入采购金额。

### 5.3 订单截图识别

1. 用户选择 1 至 5 张同一订单的截图；页面提示优先选择包含商品明细和实付金额的订单详情页。
2. 图片上传后显示识别状态。失败时保留图片和可继续编辑的手动表单，不丢弃用户输入。
3. 复核页展示原图缩略图、平台、订单日期、实付总额和商品明细。每个商品行允许编辑商品名、规格、数量、单位、金额，并选择“加入库存”“关联待购项”或“跳过”。
4. 系统可推荐与待购项/库存项的匹配结果，用户确认匹配关系后才生效。未识别出的内容保持为未处理行，不自动猜成库存商品。
5. 用户点击“确认采购”后展示落账摘要。支出按订单实付总额记一笔；商品入库按用户勾选的商品行分别记库存流水。
6. 成功页提供查看库存、查看支出和删除原始截图入口；再次打开已确认导入时不重复入库或记账。

识别页需能区分“处理中、识别完成待核对、识别部分成功、失败、已确认、已取消”。按钮在请求期间禁用，避免重复提交。

## 6. 截图识别与审核流程

建议采用“图像 OCR + 结构化解析 + 规则校验 + 用户复核”的流程。OCR 返回文字和位置证据；结构化解析器生成订单与商品草稿；业务代码校验日期、数量、金额范围和总额；客户端将低置信字段突出显示。

```mermaid
flowchart LR
    A[选择订单截图] --> B[家庭权限与图片校验]
    B --> C[私有媒体存储]
    C --> D[OCR 文字与位置]
    D --> E[结构化订单草稿]
    E --> F[金额/数量/置信校验]
    F --> G[用户编辑与确认]
    G --> H[事务：库存流水、库存数量、支出、待购状态]
```

建议抽取的订单字段：平台、订单日期、订单号（可选）、币种、实付总额、商品明细。商品行包含原始标题、识别出的规范名称、规格、数量、单位、单价/行金额（识别到时）、识别置信度、证据文字及图片位置。地址、电话、收件人、支付账号等信息不进入结构化结果。

金额采用订单实付总额作为支出唯一来源，避免将商品标价、优惠、运费和实付款重复相加。首期只自动处理已支付订单；取消和退款截图提示用户手动处理。订单号不是必需字段，也不应作为长期明文保存的理由。

OCR 与文本解析应有 Provider 接口，使用现有 OCR 配置作为配置入口，但不得假设配置项本身已经提供识别能力。Provider 超时或返回无效结果时保留导入记录并允许重试。首期可以同步完成一次识别请求并持久化中间状态；同一导入 ID 重试应复用记录，避免重复创建任务。

## 7. 数据模型建议

### 7.1 待购买项 `shopping_list_items`

建议字段：`id`、`family_id`、`created_by`、`name`、`brand`、`specification`、`category`、`quantity`、`unit`、`note`、`priority`、`status`、`matched_inventory_item_id`、`completed_at`、时间戳和软删除时间。状态首期为 `todo / purchased / dismissed`。待购项是独立实体，不直接以 `inventory_items.quantity = 0` 表示。

### 7.2 采购导入与明细

`purchase_imports` 保存 `family_id`、创建者、平台、订单日期、实付总额、币种、识别状态、媒体引用、识别版本、错误摘要、确认时间和支出关联。`purchase_import_lines` 保存原始标题、规范名称、规格、数量/单位、行金额、置信度、证据、待购/库存匹配关系及是否入库。

导入记录的确认状态是防止重复写入的关键。可以在支出和库存流水中保存 `source_type/source_id` 并加唯一约束，或用采购导入 ID 建立唯一关联。一个导入确认只能生成一笔订单支出；每个选择入库的商品行只能生成一次入库流水。

### 7.3 现有库存和流水

继续以 `inventory_items` 表示当前数量，以 `inventory_transactions` 表示不可变增减流水。新增 `reason` 规范值或来源引用，如 `opening_balance`、`manual_adjustment`、`purchase_import`、`consumption`。库存数量更新和流水创建必须在同一数据库事务内。已有库存需要在启用流水重算前建立期初流水，避免重算时将既有数量清零。

采购商品匹配需要考虑品牌和规格，避免把不同配方或不同重量的猫粮合并。可先在库存项增加可选 `brand/specification` 字段；规范化名称和模糊匹配只生成候选，最终由用户确认。

### 7.4 支出关联

保留现有家庭 `expenses` 作为月度统计来源，增加可追溯到采购导入的引用或独立订单关联。一个订单默认只生成一笔实付金额支出；若用户关闭“记入支出”，则只更新库存与待购状态。

## 8. API 草案

所有路由位于家庭作用域下，并复用现有认证和家庭权限校验。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET / POST | `/families/{familyId}/shopping-list` | 查询、创建待购买项 |
| PATCH / DELETE | `/families/{familyId}/shopping-list/{itemId}` | 修改、完成或移除待购买项 |
| POST | `/families/{familyId}/purchase-imports` | 上传截图并创建导入草稿 |
| GET | `/families/{familyId}/purchase-imports/{importId}` | 查询识别状态、草稿和结果 |
| POST | `/families/{familyId}/purchase-imports/{importId}/recognize` | 启动或重试识别 |
| PATCH | `/families/{familyId}/purchase-imports/{importId}` | 保存用户修订后的订单草稿 |
| POST | `/families/{familyId}/purchase-imports/{importId}/confirm` | 幂等确认采购并落账 |
| POST | `/families/{familyId}/inventory/{itemId}/adjustments` | 记录手动库存调整流水 |

确认请求应携带草稿版本或幂等键。服务端校验导入、商品行、关联库存项和待购项全部属于当前家庭；跨家庭 ID 返回不可见资源错误。OpenAPI 与前后端 DTO 应由同一字段语义维护。

## 9. 安全、隐私与故障恢复

- 图片只允许家庭成员访问，存储路径使用不可猜测对象键；校验文件签名、格式、大小和数量，不信任文件扩展名。
- 订单截图可能包含个人地址和联系方式。解析时只提取采购需要的字段；原图设可配置保留期限，建议确认后短期保留并允许用户立即删除。存储期限最终应与隐私政策一致。
- 上传、识别、修改草稿、确认和删除均校验家庭权限；接口限流，Provider 密钥只保留在服务端配置。
- 识别失败不影响手动添加；确认事务失败不留下部分库存或支出。需要提供重试、取消未确认草稿和已确认采购的冲正流程。
- 修改已确认采购不直接覆盖历史流水，通过反向流水或冲正记录更正，支出也需关联修正。

## 10. 分阶段实施

### 阶段 A：库存台账与待购买清单

- 增加待购表、家庭级 API 和小程序“库存 / 待购买”页签。
- 增加库存手动调整入口，所有新增、补货、消耗和纠错都写入流水。
- 为现有库存建立期初流水；补齐权限、并发和数量重算测试。
- 首页库存卡展示待购数量和低库存摘要。

### 阶段 B：截图上传与识别复核

- 建立通用私有媒体上传能力及采购导入/商品明细表。
- 接入 OCR Provider 和结构化解析，支持淘宝、京东清晰的已支付订单详情截图。
- 完成识别状态、字段置信度、证据回看、草稿编辑、重试和删除。
- 建立经脱敏的截图样本集，覆盖单商品、多商品、长标题、优惠和截图裁切；依样本评估字段准确率。

### 阶段 C：采购确认与跨域落账

- 确认采购时，将订单支出、库存流水、库存数量和待购完成状态放在事务中提交。
- 增加唯一约束和重复提交测试，支持确认失败后安全重试。
- 加入库存候选匹配、商品规格字段、采购历史查询与冲正。
- 根据真实样本扩展平台和截图类型，再评估部分退款、多图合并等边界。

### 阶段 D：H5 复用与体验增强

- H5 复用同一待购和采购 API，完善采购历史、过滤与库存流水查看。
- 根据使用反馈增加常买清单、快捷补货、商品别名和家庭协作提示。
- 只有形成连续可靠的消耗流水后，才评估库存耗尽预测；不得以不完整记录推断“没有消耗”。

## 11. 测试与验收

### 后端

- 单元测试：解析正常/模糊标题、数量单位、金额、日期、优惠、低置信字段和无商品明细。
- API 测试：未授权、跨家庭资源、错误媒体格式、超限文件、OCR 超时、重试和草稿版本冲突。
- MySQL 集成测试：确认采购事务、重复确认、并发确认、库存流水与数量一致、支出只生成一次、冲正后可重算。
- 迁移测试：空库升级、已有库存期初流水、重复迁移和回滚策略。

### 小程序

- 手动新增/编辑/完成待购项；从库存不足项加入待购；网络失败后可恢复草稿。
- 上传、处理中、识别部分成功、识别失败、低置信提示、用户修订、取消和确认状态完整。
- 多商品订单只入库用户选择的商品；重复点击确认不重复增加数量和支出。
- 页面在小屏和长商品名、长规格、金额较大时不发生文字溢出或按钮遮挡。

### 建议验收门槛

- 所有正式库存与支出变更必须经过用户确认；识别失败仍可手动完成采购记录。
- 对冻结的脱敏订单截图集分别统计平台、订单日期、商品行、数量和实付总额的精确率/召回率，并在开发 Provider 前确定目标值；低置信字段必须可见且可编辑。
- 同一采购导入重复确认任意次数，库存和支出仍只落账一次；确认失败不会产生部分落账。
- 用户能从库存数量追溯对应流水，并能通过冲正修复已确认的错误采购。

## 12. 首期交付定义

首期完成后，用户应能从家庭页进入待购清单，手动添加物品，上传淘宝/京东订单截图，检查并修改识别结果，选择需要入库的商品，确认后看到正确库存、流水和可选支出。识别是录入辅助，不替代用户核对，也不代表系统已连接购物平台。
