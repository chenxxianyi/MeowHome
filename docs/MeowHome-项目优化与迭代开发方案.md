# MeowHome 项目优化与迭代开发方案

> 版本：v1.0  
> 盘点基准：2026-10-22 仓库代码与现有开发文档  
> 文档目的：基于当前实现确定产品定位、发布前风险和后续开发顺序。本文是新的迭代路线图，不替代疫苗、Agent、前端、后端的专项设计文档。

## 1. 项目判断

MeowHome 已具备较完整的猫咪家庭照护产品骨架，包含 Go/Gin/MySQL 后端、UniApp 微信小程序、Vue H5 前端和静态 Demo。猫咪档案、日常记录、记录日历、基础提醒、疫苗建议与提醒关联、库存账目、时光页面和猫管家 Agent 均已有不同程度的实现。

当前更适合定位为**功能较丰富的内测版**。项目尚未达到统一发布状态，主要原因是：客户端功能和数据来源不一致；数据库迁移依赖单独操作且缺少服务启动前的版本检查；核心记录和资产维护接口不完整；提醒尚未形成系统通知闭环；Agent 与微信端仍有真实环境验收项。

### 1.1 产品目标

帮助一个养猫家庭持续、可靠地完成四件事：

1. 建立猫咪和家庭照护档案。
2. 低负担记录健康、生活和接种情况。
3. 把接种、复诊、用药等事项变成可管理、可触达的待办。
4. 让家庭成员基于可信记录协作，并能查看、导出和保护自己的数据。

### 1.2 当前客户端定位建议

根据当前调试和使用路径，建议暂定**微信小程序为首要发布端**，作为真实用户流程和质量验收的基准。H5 在完成真实数据、功能一致性和发布验收前，定位为内部预览/演示端；静态 Demo 仅用于交互展示。

若后续决定 H5 也作为正式客户端，应按同一套接口契约、权限规则、业务功能和验收标准补齐，不维护独立的 Mock 业务真相。

## 2. 当前功能盘点

“已实现”表示仓库中已有对应代码，不代表已完成生产环境或真实设备验收。

| 功能域 | 当前状态 | 后续判断 |
|---|---|---|
| 登录、家庭和猫咪档案 | 已具备基础服务和页面 | 补齐成员邀请、角色管理和完整协作闭环。 |
| 日常记录与记录日历 | 小程序已有记录表单、日历浏览、记录列表/详情和撤销入口；后端支持查询、新增、更正、软删除和审计 | 记录更正表单尚未接入客户端；继续覆盖日历筛选、分页、家庭时区和失败状态。 |
| 疫苗记录与待办 | 已有专属表单、有限规则建议、日期选择、来源关联和接种后完成待办 | 目前仅对部分疫苗和接种情形提供建议；扩展规则前需要兽医/指南评审。提醒仍需真实通知能力。 |
| 普通提醒 | 已支持创建、查询、完成等基础流程 | “稍后”仍是未开放提示；未形成周期调度和系统通知闭环。 |
| 用药、驱虫、复诊 | 可通过通用记录/提醒承载部分信息 | 尚无完整的药物、计划、打卡和周期提醒领域流程。 |
| 库存与账目 | 已有列表和新增路径 | 需要补充修改、停用/删除、库存增减流水、分类统计和错误恢复。 |
| 时光和媒体 | 有时光数据与页面基础 | 记录照片上传尚未接通完整存储流程。 |
| 病历与 OCR | 页面有本地预览和说明 | 上传、存储、OCR、指标确认和证据查看均未形成真实闭环。 |
| AI 记录与摘要 | 后端当前采用确定性规则解析/摘要 | 界面应区分规则整理与模型生成；模型能力需单独接入和验收。 |
| 猫管家 Agent | 已有巡检、聊天、证据和待办草稿等较多代码 | 专项清单仍有未完成项；真实模型、真实设备和多实例调度边界需要验收。 |
| H5 前端 | 部分页面调用真实后端，部分功能仍读 Mock | 决定是否正式支持；正式支持时需消除演示数据混用。 |
| 导出、备份和恢复 | 当前主路由中未形成完整能力 | 作为真实用户数据长期保存前的重要基础能力。 |

## 3. 迭代原则

1. **先保数据正确，再扩展智能能力。** 页面显示为空、请求失败和确实没有数据必须能被用户区分。
2. **一项业务只保留一个权威数据来源。** H5、微信小程序、Agent 和后端共用 API 契约与业务规则。
3. **先闭合用户流程，再增加页面。** 每项能力都覆盖创建、查看、修改、失败恢复和权限边界。
4. **医疗内容可解释、可人工确认。** 规则建议显示适用条件、日期来源、版本和依据；不适用时要求用户或兽医给出日期，不用模型猜测医疗安排。
5. **日期按家庭时区处理。** 以日期为主的疫苗/待办字段不能由 UTC 字符串截取生成本地日期。
6. **“构建成功”与“可发布”分开验收。** CI、数据库集成测试、微信开发者工具、真机和真实模型各自记录结果。

## 4. 分阶段开发计划

开发阶段按依赖排序，不预设人日。前一阶段的验收项通过后再将后续阶段标记为完成。

### 阶段 0：发布基线与数据可靠性

**目标：** 任何开发者都能识别当前代码版本、数据库结构和客户端构建状态；减少因环境不一致导致的运行错误。

**开发任务**

- [ ] 确认正式发布端。按当前使用情况以微信小程序为首发端；H5 明确标为演示端，或纳入同等功能开发。
- [x] 建立数据库迁移版本记录和服务端结构检查。启动时发现缺少迁移会给出当前/目标版本和命令；已有数据库可显式 baseline。
- [x] 保持迁移由显式部署步骤执行；迁移命令只应用未记录版本，`-down` 只回滚最近一次，不由服务启动自动改表。
- [ ] 补齐 OpenAPI 中的记录列表/新增/详情/更正/撤销路由；今日状态、趋势、提醒、时光、库存、账目、AI 等契约和完整路由差异检查仍待补齐。
- [x] 增加 CI 质量门禁：Go 格式、vet、build、测试；小程序类型检查、微信构建和脚本测试；H5 类型检查、构建和单元测试。
- [x] 为依赖 MySQL 的集成测试提供 CI MySQL 服务；未配置数据库的本地运行仍会明确显示跳过。
- [ ] 发布构建中移除标签/图标测试页面；检查并清理仓库中不应提交的生成二进制文件。
- [x] 建立根目录项目说明和服务端配置样例，记录本地启动、迁移、构建、测试和手机调试入口。

**验收标准**

- 新环境按文档可启动数据库、执行迁移、启动后端并编译小程序。
- 迁移未执行时服务能明确报告当前/目标结构版本。
- CI 配置覆盖后端、微信小程序、H5 和带 MySQL 的集成测试；需以实际 CI 运行确认工作流状态。
- OpenAPI 能覆盖对外业务路由，接口字段和错误码可追溯。

### 阶段 1：记录和提醒核心闭环

**目标：** 用户可以放心录入、回看、更正记录，并且不会因为提醒失败或重复操作丢失待办。

**开发任务**

- [x] 后端为记录增加完整字段更正和软删除接口；服务端校验猫咪家庭归属、保留创建者/创建时间并写入审计动作。
- [x] 小程序记录详情提供二次确认撤销入口；更正表单尚未接入客户端。
- [ ] 记录日历覆盖月份查询、分页完整性、猫咪/类型筛选、空状态、加载失败重试和新增后的刷新。
- [ ] 统一提醒状态：待办、今天到期、逾期、已完成、已取消/跳过；界面明确说明逾期只表示计划日已过。
- [ ] 实现提醒延期和修改日期；所有更新使用服务端校验、幂等和冲突反馈。
- [ ] 明确提醒触达方案。先完成应用内到期展示；再按微信能力接入用户授权的订阅通知，并提供授权拒绝和发送失败时的应用内兜底。
- [ ] 为需要重复执行的用药、驱虫和复诊定义周期与实例生成规则，避免一次性提醒被误当成周期任务。
- [ ] 统一家庭时区、服务器时间和日历日期的转换；增加跨日、夏令时/时区缺省和历史记录测试。
- [ ] 将 H5 的列表和详情与小程序对齐，或在 H5 上明确演示数据和可用范围。

**验收标准**

- 重复点击、网络重试和并发操作不会生成重复记录或重复待办。
- 修改和撤销后，日历、今日页、提醒页及统计结果一致刷新。
- 请求失败不会被渲染成“没有记录”或金额/数量为 0 的正常结果。
- 在家庭时区下，用户选择的记录日期和提醒日期前后端一致。

### 阶段 2：家庭协作和资产维护

**目标：** 家庭不只是单人档案集合，成员可以按权限共同照护；库存和费用能够持续维护。

**开发任务**

- [ ] 设计邀请流程：邀请码/邀请链接、过期、重复邀请、撤销和加入确认。
- [ ] 明确 owner/admin/member 权限矩阵，并在服务端逐路由执行；客户端仅展示权限结果，不承担最终授权。
- [ ] 提供成员角色调整、移除、离开家庭和所有者转移流程，并记录审计事件。
- [ ] 为库存增加数量调整流水、低库存阈值、补货状态和历史查看；区分“当前库存”与“库存流水”。
- [ ] 为账目增加修改/撤销、分类、按月统计和家庭币种处理。
- [ ] 对家庭成员变更、猫咪删除和记录归档明确影响范围及二次确认文案。

**验收标准**

- 家庭 A/B 的成员不能读取或修改另一家庭的数据。
- 不同角色对邀请、记录、库存和账目的操作符合权限矩阵。
- 库存调整可由流水重算；已完成账目不会因重复提交重复计入。

### 阶段 3：媒体、病历和数据可携带性

**目标：** 用户能安全保存照片和医疗资料，并在需要时导出或恢复自己的数据。

**开发任务**

- [ ] 统一媒体上传服务：文件类型、大小和内容校验，进度、取消、失败重试、预览、访问鉴权和删除。
- [ ] 接通时光照片及记录附件；在弱网和上传失败时保留用户输入。
- [ ] 病历上传形成完整状态机：上传、待识别、识别失败、草稿复核、确认入档。
- [ ] OCR 结果必须可编辑并能回到原图/页码证据；异常标记由确定性规则产生，模型不得自行提高风险等级。
- [ ] 提供 JSON 完整导出及便于阅读的记录/就诊报告；明确下载有效期和家庭权限。
- [ ] 设计备份、恢复预检、确认、失败回滚和数据删除策略。

**验收标准**

- 上传失败不丢失表单内容，未确认的 OCR 草稿不进入正式健康档案。
- 用户可定位摘要或指标所引用的原始记录/文件。
- 导出文件可以校验完整性；恢复不会覆盖未确认的数据。

### 阶段 4：Agent 与 AI 能力验收

**目标：** 清楚区分确定性规则和模型能力，确保 Agent 的建议有证据、操作有确认、故障可恢复。

**开发任务**

- [ ] 将自然语言记录解析和今日摘要标记为“规则整理/规则摘要”，或按专项方案接入真实模型；不得让 `rule-based-v1` 被误解为真实模型结果。
- [ ] 建立固定业务评测集，覆盖漏字段、多猫歧义、否定表达、时间、单位、健康风险文本和无记录情况。
- [ ] 真实模型联调记录 Provider、模型、提示词版本、耗时、失败类型、用户修改率和确认成功率。
- [ ] Agent 草稿需校验家庭/猫咪、未来计划日期、过期时间、版本冲突、重复确认和软删除对象；正式提醒只能在用户确认后创建。
- [ ] 保持回答和行动引用授权范围内的证据；证据不足时明确返回“未找到/数据不足”，不能把查询失败当作零条记录。
- [ ] 单实例部署前显式限制实例数；多实例前为巡检任务增加数据库领取锁或等价的分布式互斥。
- [ ] 在微信开发者工具和真机完成登录、家庭切换、记录确认、草稿恢复、提醒确认和退出登录流程。

**验收标准**

- Fake Provider 测试和真实模型人工评审分开记录；前者不代表真实模型质量。
- Agent 不能绕过用户确认创建正式提醒或记录。
- 同一家庭在多设备和重试条件下不会产生重复 Agent 消息/提醒。
- Agent 关闭、模型超时或响应不合规时，手工记录和提醒流程仍正常。

## 5. 疫苗专项后续要求

疫苗记录、有限日期建议和关联待办已构成 MVP 基础。后续迭代沿用 [疫苗记录与提醒开发方案](MeowHome-疫苗记录与提醒开发方案.md)，并重点完成：

- [ ] 将规则从散落的条件分支逐步整理成有版本、来源、生效范围和停用状态的规则数据。
- [ ] 每条建议保存规则版本、适用条件、日期来源和用户确认日期，历史建议可解释、可复核。
- [ ] 扩展疫苗系列前先评审年龄、既往接种史、产品说明、地区规定及规则边界；无匹配规则时继续提供手动日期。
- [ ] 提醒完成关联接种记录后，刷新该猫咪的系列进度并判断是否存在可生成的下一步建议。
- [ ] 通过真实业务样例和兽医/权威指南审阅验证规则，不把通用间隔表达为强制接种安排。

## 6. 数据、隐私与运行要求

- 所有家庭数据访问必须由服务端校验用户与家庭成员关系；所有猫咪级写入必须校验猫咪属于该家庭。
- 认证信息、模型密钥和数据库凭据仅存在服务端配置，不写入小程序包、H5 静态资源或日志。
- 日志记录请求 ID、业务对象 ID 和错误码；不记录密码、完整医疗文档、访问令牌或不必要的原始对话。
- 用户退出家庭、删除猫咪、删除账号、媒体过期和备份恢复需要明确的保留/清理规则。
- 每次数据库结构变更提供 Up/Down 或向前修复方案、兼容性说明和数据备份要求。
- 上线前分别完成开发、预发布和生产配置核对；预发布验证迁移、文件、通知、Agent 降级和备份恢复。

## 7. 质量门禁与完成定义

每个功能进入“完成”状态前，至少具备：

1. 后端业务校验、家庭权限和错误码覆盖。
2. 数据迁移和回滚/修复说明。
3. OpenAPI 契约和小程序/H5 DTO 对齐。
4. 正常、空数据、失败、重复提交、并发或重试等相关测试。
5. 微信构建；涉及微信授权、上传或通知时完成开发者工具/真机验证。
6. 用户操作说明、已知限制和日志/监控指标。

发布候选版本必须完成：

- [ ] Go 全量测试、vet、build 通过。
- [ ] 小程序类型检查、脚本测试和微信生产构建通过。
- [ ] H5 若作为正式客户端，类型检查、单元测试和生产构建通过。
- [ ] 干净数据库迁移和升级数据库迁移均通过；MySQL 集成测试没有被误记为跳过通过。
- [ ] 核心流程真机验收：注册/登录、家庭和猫咪、记录/更正、疫苗待办、提醒触达、弱网恢复。
- [ ] 权限和敏感数据检查通过；导出/恢复和删除策略有可复验记录。
- [ ] Agent/模型功能有独立的真实模型评审结果；未完成时可通过配置关闭，不影响基础业务。

## 8. 暂缓事项

分享广场、复杂社交互动、更多装饰性看板和未验证的 AI 自动诊疗暂不进入近期主线。先确保家庭记录可信、提醒按计划触达、成员协作权限清晰、数据能导出恢复，再根据用户反馈决定是否投入。
